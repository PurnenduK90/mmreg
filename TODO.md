## Direction

mmreg is the **one tool for memory-mapped registers on Linux**: a Rust library with C and Python
bindings, and a CLI. It replaces both kinds of tool people use today:

- **`devmem` / `devmem2`** for ad-hoc access by address (`mmreg read|write <address>`), with
  blueprint and pre-flight checks so a typo does not hang the bus. Raw `/dev/mem` access is
  compiled in only with the `debug` feature, so release builds cannot reach arbitrary physical
  memory;
- **per-project UIO helper libraries** (open `/dev/uioN` by name, locked read/write/modify,
  interrupt wait), so applications in any language share one implementation and one lock
  protocol.

mmreg stays **generic**: it knows no SoC, board, register generator or project. Projects depend on
mmreg; mmreg depends on none of them. Hardware knowledge comes in two ways:

- **Production:** code generated by the project's register generator (C headers, Rust constants)
  is compiled into the program, which uses mmreg for offset access, locking and interrupts.
  Nothing is parsed at run time.
- **Debug and experiments:** the Python package reads **block files**
  ([`mmreg-block/1`](docs/users/07-block-files.md), JSON) for access by name, field decoding and
  access-type safety. A generator emits them as one more output, an importer converts CMSIS-SVD
  (later IP-XACT), or a person defines registers inline in Python. The Rust core, C library and
  CLI never parse them; the CLI works by address.

Footprint stays a feature: mmreg competes with single-file `devmem2`. `libc` is the only mandatory
dependency; anything needing a parser sits behind a cargo feature. A production build has no
`/dev/mem` access and no parser, and can leave out the CLI.

mmreg must build where embedded Linux is built: the Rust of current Yocto and Buildroot LTS
releases, not only the latest stable.

**Background for this roadmap** (the use case, kernel UIO interface, the helper-library API to
cover, build environments, testing without hardware):
[docs/developers/05-roadmap-reference.md](docs/developers/05-roadmap-reference.md).

### Milestones at a glance

| Version | Delivers | A project can drop |
|---|---|---|
| **1.0.0** | first stable API: Rust 1.75, `debug` feature, UIO lock protocol, width-aware `MemoryMapper`, `#[non_exhaustive]` public enums | `devmem` in release images |
| 1.0.x | fixes only | — |
| **1.1** | `Device` (UIO by name, shared handle, sequence guard, IRQ), 8–64-bit access, warnings API | `devmem`; UIO helper libraries **for Rust users** |
| **1.2** | C ABI and Python binding (offset access, locks, IRQ, inline `define()`) | UIO helper libraries **for C / Python users** |
| 1.3 | Python by name: block files, field decoding, access-type safety, `dump` | hand-decoded register dumps |
| 1.4 | CLI tools: block read, `watch`, `irq`, JSON output; SVD importer (Python) | ad-hoc polling scripts |

**Versioning follows [SemVer](https://semver.org/).** 1.0.0 is the first stable API: everything
incompatible went in before it was tagged. Minor releases (1.1, 1.2, ...) only add: public enums
and the register structs are `#[non_exhaustive]`, so new variants and fields are not breaking.
Patch releases (1.0.x) only fix. Anything incompatible waits for 2.0.

A project whose tools are written in C needs **1.2** to replace its UIO helper library and `devmem`;
block files (1.3) are not required for that, because C tools use offsets from their own generated
headers.

### Layering (target, 1.1)

```text
mmio::Mapping      unsafe mmap + volatile 8/16/32/64-bit access (only unsafe module)
Device             one register window: UIO by name / path, or /dev/mem (debug);
                   offset access, lock protocol, sequence guard, IRQ; Send + Sync, &self
Interface          named registers and fields on top of a Device (today's API)
C ABI              thin wrapper over Device (1.2)
Python             ctypes over the C ABI (1.2); by-name layer on block files (1.3, Python only)
CLI                parsing and printing only; by address / UIO name + offset
```

Generated code (C headers, Rust constants) uses `Device` offsets directly; no mmreg type is needed
for it.

### Cargo features (target layout)

| Feature | Adds | Default |
|---|---|---|
| *(core)* | `Device` over UIO, `Interface`, locking, interrupts, blueprint and pre-flight checks | always |
| `debug` | `/dev/mem` backend for addresses no UIO device covers (debug and bring-up builds; since 1.0.0) | off |
| `profile` | JSON safety profiles (since 1.0.0) | on |
| `capi` | C ABI (`libmmreg.a`, `libmmreg.so`, `mmreg.h`); the Python binding uses it | off |

Block files add no feature: they are read by the Python package (standard-library `json`), not by
the Rust crate.

Example builds: CLI for development images = `--features debug`; CLI for release images =
defaults (UIO only); library for production applications = `--no-default-features --features capi`
(UIO only, no parser).

Without `debug`, `mmreg read|write <address>` still works for any address inside a UIO device's
region; other addresses are refused with `[E_DEBUG_DISABLED]` before anything is opened. Safety
profile checks read registers by physical address too, so outside UIO regions they also need
`debug`.

### Lock protocol (documented, so other programs can join)

- **UIO-backed access (since 1.0.0):** exclusive `flock` on an open `/dev/uioN`, per access. Any
  program that takes `flock(LOCK_EX)` on the same device excludes and is excluded by mmreg,
  whatever its language.
- **`/dev/mem` access (`debug`) and custom mappers:** per-page lock files (`lock.rs`).
- **Within a process:** `flock` does not exclude threads sharing one open file and does exclude two
  handles of one process on the same device. So a `Device` serialises its own threads with a mutex,
  handles to the same device in one process share one open file (a per-process registry keyed by
  `(st_dev, st_ino)` so symlinks and relative paths share one descriptor, plus page lock files for
  `/dev/mem`), and the sequence guard is reentrant (mutex plus depth count).
- **Sequences:** a guard held across several accesses (read-modify-write chains, multi-word reads,
  FIFO drains).

## Review notes (1.0.0 code, basis for the items below)

- `Interface` needs `&mut self` for every access (the `raw` cache), so one handle cannot be shared
  between threads; bindings and multi-threaded applications need a `&self`, `Send + Sync` handle.
- `Interface` opens `/dev/uioN` a second time for the lock; the mapping's own file is closed after
  `mmap`, so there is no descriptor to wait on for interrupts. `Device` (1.1) keeps one file for
  mapping, lock and interrupts.
- Each access opens (and may create) a lock file, `flock`s and closes it; each
  `read_register_at` also scans sysfs and maps/unmaps. Fine for the CLI, costly for a library
  reading a data register in a loop.
- UIO devices are always opened read-write, so read-only tools need write permission on
  `/dev/uioN`.
- `write_subregister` read-modify-writes the whole register, clearing pending W1C bits.
- Four `eprintln!`s in `memcheck.rs` (clock count, runtime PM guard) print from the library.
- Safety-profile checks read through `read_register_at(addr, true)`, i.e. `/dev/mem` for SoC
  registers: outside UIO regions they need a `debug` build.

## 1.1 — library core (replaces `devmem`, and UIO helper libraries for Rust)

- [x] **`Device`:** one register window, `&self` access, `Send + Sync`, owns the mapping and the
  open device file.
  - `Device::open_uio(name)` finds `/dev/uioN` from `/sys/class/uio/uio*/name`, region from
    `maps/mapN` (`.region(n)` to pick another); `open_uio_path("/dev/uio3")`;
    `open_addr(base, size)` (UIO region covering it, else `/dev/mem` with `debug`).
    `uio::find(name)` returns the device path. Two devices with one name are
    `[E_UIO_AMBIGUOUS]`; no device is `[E_UIO_NOT_FOUND]` listing the names present.
  - Must cover every call of a typical UIO helper library (table in
    [Roadmap Reference → The API to Cover](docs/developers/05-roadmap-reference.md#the-api-to-cover-uio-helper-library)),
    so ports are mechanical.
  - `.read_only()`: `O_RDONLY` + `PROT_READ`, so read-only tools work with read permission only.
  - `read_u8/u16/u32/u64(offset)`, `write_*`, `update_u32(offset, mask, value)` (locked RMW).
  - Blueprint, pre-flight and safety-profile checks run once at open.
- [x] **Lock protocol within a process:** one open `/dev/uioN` (or `/dev/mem` page lock file) per
   `(st_dev, st_ino)` and process (registry) shared by its `Device` handles, a mutex for threads;
  the inter-process protocol is unchanged.
- [x] **Sequence guard:** `let _g = dev.lock()?;` holds the lock until dropped; reentrant.
- [x] **Interrupts (UIO):** `irq_unmask()`, `irq_wait(timeout) -> Option<count>` (`poll` + `read`).
  Document "clear the source, then unmask" for level-triggered sources.
- [x] **`Interface` on `Device`:** today's named-register API kept as a layer over `Device`
  (constructors and accessors unchanged where possible); `write_subregister` keeps its
  read-modify-write semantics (access types are handled by generated code and the Python layer).
- [x] **Generated-code guide** (`docs/users/`): how generated C headers and Rust constants use
  `Device` (offset, mask, shift; `update_u32` for read-modify-write), and which access-type rules
  a generator should apply in the field writers it emits (W1C / pulse fields written without
  read-modify-write), so production code is as safe as the Python debug layer.
- [x] **No stderr from the library.** Return the `memcheck.rs` warnings to the caller (a warnings
  list or callback on `Interface` / `Device`) and let the CLI print. Prerequisite for the bindings,
  which must not write to a host program's stderr.
- [x] **CLI:** `--width 8|16|32|64` on `read` / `write`; `read|write <uio name> <offset>` for UIO
  devices (works without `debug`); `--version` showing the enabled features.
- [x] **Tests:** lock protocol (two processes, two threads, nested guard), read-only open, name
  lookup (duplicates, missing), IRQ wait and unmask with a fake device; approach in
  [Roadmap Reference → Testing Without Hardware](docs/developers/05-roadmap-reference.md#testing-without-hardware).
- [x] **User docs:** setting up UIO (Device Tree `generic-uio`, `uio_pdrv_genirq.of_id`, udev
  permissions), from the Roadmap Reference.

## 1.2 — C and Python bindings (replaces UIO helper libraries for C / Python)

- [ ] **C ABI (`capi` feature):** `cdylib` + `staticlib`, opaque `mmreg_dev *`, `int` error
  returns with `mmreg_last_error()` (code + message, thread-local), no panics across the boundary.
  The release profile's `panic = "abort"` applies to the library too, so a panic would kill the
  host program: no `unwrap`/indexing panics on the C path (clippy `unwrap_used` / `indexing_slicing`
  denied in the `capi` module), and `catch_unwind` at every entry for builds that unwind.
  `mmreg_open_uio(name, flags)`, `mmreg_open_uio_path`, `mmreg_open_addr`, `mmreg_close`,
  `mmreg_rd{8,16,32,64}`, `mmreg_wr{8,16,32,64}`, `mmreg_update32`, `mmreg_lock` /
  `mmreg_unlock`, `mmreg_irq_unmask`, `mmreg_irq_wait` (1 interrupt / 0 timeout / -1 error,
  count out-parameter), `mmreg_find_uio(name, buf, len)`, and an `MMREG_FIELD(v, mask, shift)`
  macro for generated headers.
- [ ] **`mmreg.h`:** checked in, with a test comparing it with the exported symbols (cbindgen as
  a dev-only step). `mmreg.pc` for `pkg-config`; static library usable without Cargo at link time.
- [ ] **C example and test:** small C program against the static library, built and run in CI,
  including the lock interop test (C and Rust processes on one mock device).
- [ ] **Python binding:** pure-Python package (`bindings/python/`) using `ctypes` on
  `libmmreg.so`, so targets need no compiler, PyO3 or wheel build. Context managers for the device
  and the lock; `MmregError` carrying the `[E_*]` code. Same API shape as Rust. Inline
  definitions for experiments without a block file: `d.define("CTRL", offset=0x8,
  fields={"EN": "0"})`, then `d.CTRL.EN = 1`.
- [ ] **Packaging notes** for Yocto and Buildroot (constraints in
  [Roadmap Reference → Build Environments](docs/developers/05-roadmap-reference.md#build-environments)):
  library-only build (`--no-default-features --features capi`), static library + header + `.pc`,
  Python module; release-image CLI vs `debug` CLI; an example Yocto recipe in `docs/`.

## 1.3 — Python by name (block files, debug and experiments)

Specification: [docs/users/07-block-files.md](docs/users/07-block-files.md) (draft; freeze when
this version ships). Everything here is in the Python package; the Rust crate, C library and CLI
do not change.

- [ ] **Loader and validation:** JSON with the standard library; strict keys with the `x-` escape,
  version check, overlap / alignment / bounds / enum checks, `dim` expansion, case-insensitive
  unique names. Every error names the file, register and field.
- [ ] **Name resolution:** instance files, then UIO name → `of_node/compatible` → block file, with
  the search paths of the spec. `mmreg.list()` shows the instances found and whether their device
  is present.
- [ ] **Access by name:** `d.CTRL`, `d.CTRL.ENABLE = 1`, enum names, arrays (`d.DATA[3]`),
  `d.dump(diff_reset=True)`; registers print decoded.
- [ ] **Access-type rules** from the spec (write only what was asked, no read side effects without
  `side_effects=True`, refused accesses).
- [ ] **Wide registers** (`regwidth` > `accesswidth`): word order from the spec, under one lock.
- [ ] **Instance checks** run like a safety profile before first access.
- [ ] **`python -m mmreg check <file>`** for generators' CI (validate, no hardware access).

## 1.4 — CLI and Python tools

- [ ] **Block read (CLI):** `read <addr | uio name + offset> --count N` (hexdump-style, one lock per
  page).
- [ ] **`watch` (CLI by address / offset, Python by name):** poll and print changes (rate-limited,
  `--interval`).
- [ ] **`irq <uio name> [timeout]` (CLI):** wait for a UIO interrupt from the shell.
- [ ] **Output formats (CLI):** `--format hex|dec|bin|json` (JSON for scripts and agents).
- [ ] **Importer (Python):** CMSIS-SVD → block files (`python -m mmreg import-svd`).

## Adoption checklist (generic)

What a project needs from mmreg before it can drop its own UIO helper library and `devmem`:

| Need | Version |
|---|---|
| Builds with the project's Yocto / Buildroot Rust | 1.0.0 |
